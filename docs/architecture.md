# Architecture

One React/TypeScript application is built by Vite into static files. HashRouter renders routes under /#/; route parameters created in the browser require no hosting rewrites. The running app currently uses Poster People host tokens, bundled Geist Serif 400 headings, Arial body and Base UI primitives. New and changed UI must follow the accepted Poster People [design system](design-system/README.md), adapted into the existing stack; installing its reference did not convert runtime styles. The browser remains the scenario data owner. An optional loopback companion or Netlify Function generates deepening proposals/questions without storing application data.

## Data flow

JSON marketplace/person fixtures → initialState → PrototypeProvider → feature views. Local operations go through transition with shared Zod schemas and explicit role/ownership/transition checks for coherent simulation. All roles still have access to the same browser data; these checks are not security.

Candidate source notes, generated draft and approved application are distinct fields. Submission snapshots CV, candidate name, job title, scenario score and summary. Employer stage events are appended, with private-in-the-UI notes. Profile/job edits do not rewrite submitted records.

Storage uses version 2 under the existing localStorage key, explicitly migrating version-1 jobs to disabled deepening and preserving old application/legacy fields. Validated configuration revisions and completed/skip snapshots are shared plain Zod schemas. Entering deepening captures job/aspect/identity/CV, durably removes any saved draft before HTTP, and retains all unfinished form data in memory only. Returning to step 1 deletes unanswered/non-refused questions and preserves decided ones. Every entry generates only missing questions, even without text edits; valid results merge atomically with preserved decisions. There is no action to replace an existing question. Failure retry requests missing questions only. Enabled step 1 requires answer validation without consent; step 2 alone displays the final approval checkbox. The ordinary one-step flow retains approval. Final send alone commits one application, independent of later job/profile edits.

Storage uses one versioned localStorage key. Import validates schema/version, unique IDs, cross-references and stage history before replacing state. Unreadable/incompatible saves are protected against automatic overwrite; settings can download the original raw save, import a valid file or explicitly reset. Failed/quota-limited persistence leaves the in-memory app usable and offers export. Import/export is capped at 2 MB; no binary CV storage.

## Features

src/features/prototype owns model/storage/state and page compositions. src/features/jobs retains reusable presentation/filter/description logic; src/components/ui owns Base UI controls. Keep changes small.

LocalStorage is origin-specific. Reload preserves state; another browser/device/port starts separately. No cross-tab live synchronization is provided. An exclusive browser Web Lock permits one editing tab; other tabs are read-only with export and takeover after closing the writer and reloading. Startup normalizes legacy storage only after acquiring that lock and re-reads the latest state before enabling writes. External storage events pause editing until reload. Unsupported Web Locks environments remain read-only. Hash links reference records in the receiving browser, not transferred records.

## Evidence and distribution

The baseline historical CSV and JSON are separate from interactive state. Future evidence must arrive in a separately reviewed package. package:participant copies only explicit allowed files/directories, including the complete docs/design-system guide/kit, and omits docs/source, historical task notes, agent run history and .git. A packet verifier checks the baseline data; packaging also verifies a pristine file/hash manifest. Ordinary checks permit participants to edit code and generate build/test output without invalidating a distribution fingerprint. Instructor repository history is never participant-safe.

## Checks

npm run check and ./scripts/verify run formatting, design-system reference integrity/example checks, lint, types, unit tests, build and Playwright against the static preview. Playwright checks external requests, complete workflows, error/recovery behavior, keyboard controls and mobile layout. No test starts system services. npm run dev starts Vite and the companion; static preview starts only Vite preview.

## Deepening transport

`npm run dev` runs `scripts/dev.mjs`: Node 24 directly executes `server/main.ts` on `127.0.0.1:3002`, while Vite runs on `127.0.0.1:3001` and proxies only `/api/deepening`. `.env.server.local` is loaded only by the companion process; the frontend imports neither the server nor its key. No extra runtime package or transpilation step is needed. `npm run build` emits the static frontend; plain preview has no generation service. Netlify separately bundles `netlify/functions/deepening.mts` with esbuild. Both transports call `server/deepening-generation.ts` for the same prompts, provider protocol, strict validation and public/professional input projection.

`src/features/deepening/client.ts` exposes `suggestAspects(job, signal?)` and `generateQuestions({revision, answer, cv, aspectIds, name}, signal?)`. Suggestions send only current public employer title/summary/description, including unsaved edits; configuration stays local until final job publication. The domain owns revisions, IDs, order and title/explanation validation. CandidateApplyForm restores the original desktop offer-left/form-right composition, with manually activated Base UI tabs inside the right sheet only when enabled. Existing fields and ordinary one-step behavior remain. Questions accept open text with an optional explicit refusal action; there is no fact checklist. Candidate application and CV text are prepared locally before HTTP. The filter removes recognized identity/contact patterns, known candidate-name tokens and lines containing recognized sensitive information; the candidate can inspect the exact prepared professional text before generation. Ordinary professional prose, uncertainty and negation remain text, not invented positive facts. An empty prepared application causes no request; an empty prepared CV is omitted. This bounded heuristic can miss private information or remove valid professional content, so use synthetic data only: it is not real-data anonymization. No PDF, profile object, contact metadata, employer notes or legacy candidate notes/generated text is sent. The strict shared schema independently checks prepared text at the HTTP boundary; the server reconstructs provider input from public job content, requested approved aspect titles/explanations and prepared application/CV text. No request/response bodies or credentials are logged. The question wire request contains `revision`, requested `aspectIds`, `applicationText` and optional `cvText`; `name` is only used locally to filter text and is not a wire field. The mounted session owns pending questions and decisions; only final send commits the combined immutable application.

POST `/api/deepening/aspects` and POST `/api/deepening/questions` independently validate strict shared Zod protocol schemas. The server reconstructs provider input from public job title/summary/description, approved aspect title/explanation and prepared professional application/CV text; it does not forward the opaque request, job/candidate identifiers or revision metadata. The Responses endpoint uses `text.format.type=json_schema`, `strict: true`, bounded output and `store: false`. Model suggestions contain only title/explanation; questions must have exactly the requested unique aspect ID set. Invalid output and refusals are unavailable results, never trusted markup or application records.

Requests are limited to 100,000 UTF-8 bytes and five seconds to receive the body. Provider JSON is limited to 64,000 bytes and 20 seconds; the browser allows 25 seconds and the same bounded response size. Two requests at most run concurrently per transport instance. Origin/Host/content-type checks limit this development boundary to the local app; no CORS access is enabled. There is no real authentication, persistent server store, body logging or API retry. Human approval, immutable final application storage and skip/retry remain client/domain responsibilities.

HTTP tests use real ephemeral loopback listeners and inject only the external provider fetch; client tests substitute the HTTP fetch boundary. Native Node loading is verified separately. No automated test spends API credit or establishes model quality. Netlify entry tests exercise the actual function with mocked provider fetches and server-only environment access, including both paths and input/origin/error boundaries. Participant packaging includes `server/`, `netlify/functions/`, the startup script and shared protocol/client, excluding environment files, instructor materials and Git history.

Retired aspect offer fragments are absent from the domain and strict AI wire schemas. Version-2 load/import uses the shared stripping object schemas to discard legacy excerpt keys from job configurations and submitted aspect revisions without changing their IDs, revision numbers, questions, decisions or identity. readState rewrites valid legacy saves in normalized form. A failed rewrite preserves the original durable save and the normalized usable memory state with the standard export warning; persisted draft tracking remains intact. Invalid saves retain the existing protected recovery path. The storage key and version-1 migration remain unchanged.

## Presentation resilience and release

ApplicationErrorBoundary surrounds the provider/router. A caught render error unmounts the writer and shows a Poster People host recovery panel with private raw-save download, reload, fixed APP-RENDER code and build identity. It never resets storage or renders/logs error text. React's caught-error handler is deliberately silent; event-handler failures and inability to load the JavaScript bundle are outside this render boundary. A build identifier combines the source revision and timestamp and is also emitted as version.json.

Netlify serves dist with the committed same-origin security/cache policy and separately deploys the generation function at `/api/deepening/aspects` and `/api/deepening/questions`. `server/hosted-deepening.ts` enforces HTTPS, canonical Origin, JSON/body limits, generic no-store responses and two in-flight calls per warm worker; the platform function configuration limits 10 calls per IP/domain per 60 seconds across both paths. This public synthetic-data service has no real authentication or global spending cap. Provider credentials are read only in the function runtime through `Netlify.env.get()`. The local companion is not exposed. Vercel remains a static alternative. scripts/release.mjs archives an already-built dist outside the repository and verifies its SHA-256 inventory without overwriting prior archives. Each remote build has its own identity. docs/PUBLICATION.md distinguishes artifact checks, local rehearsal, production smoke and actual hosted recovery evidence. Browser-local saves are not covered by hosting backups.
